1. Prompt engineering — production патерни

Системний промпт

  • Роль, сфера, обмеження, формат виходу, тон — у system.
  • Конкретні заборони: не узагальнення, а «НЕ роби X, замість цього зроби Y».
  • Версіонуйте промпти як код. Зміни — тільки з eval'юацією.

Структура повідомлень

  • Використовуйте XML/HTML-теги для секцій: <instructions>, <context>, <examples>, <input>, <reasoning>, <answer>.
  • Відокремлюйте інструкції від даних, щоб уникнути prompt injection та confusion.

Few-shot

  • 2–3 приклади — для простих задач; 4–6 — для складних класифікацій; 7–10 — для >6 категорій.
  • Включайте edge cases, реальні дані, не ідеалізовані.
  • Динамічний few-shot: ембеддити бібліотеку прикладів і діставати top-k за схожістю.

Chain-of-thought (CoT)

  • «Спочатку поясни свої міркування, потім дай відповідь».
  • Збільшує токени та латентність — використовуй тільки коли потрібна точність.
  • Для Claude: окремий thinking; для інших — явний reasoning блок.

Structured output

  • Вказуй JSON-схему, prefill { для примусу JSON.
  • Валідуй вихід через Pydantic / Zod / AJV, retry з поясненням помилки.
  • Ніколи не довіряй raw LLM output для downstream-логіки без валідації.

2. LLM evaluation

Класи метрик

Категорія Метрики / інструменти Коли
Retrieval (RAG) Context Precision, Context Recall, Context Entities Перевіряє, чи ретривер знайшов і правильно ранжував контекст
Generation Faithfulness, Answer Relevancy, Response Relevancy Чи відповідає відповідь запитанню і чи ґрунтується на контексті
End-to-end Answer Correctness, Factual Correctness, Semantic Similarity Чи фінальна відповідь правильна стосовно ground truth
Agents / Tools Topic adherence, Tool call accuracy, Tool Call F1 Чи агент не злітає з теми і правильно викликає інструменти
Класичні BLEU, ROUGE, CHRF, Exact Match Коли є еталонна відповідь

Ragas — 5 основних метрик

  • Faithfulness — чи відповідь ґрунтується на знайденому контексті? Reference-free. > 0.7 good.
  • Answer Relevancy — чи відповідає питанню? Reference-free.
  • Context Precision — чи корисні чанки ранжуються найвище?
  • Context Recall — чи знайдені всі необхідні документи?
  • Answer Correctness — чи фінальна відповідь фактологічно правильна? Потребує ground truth.

Стратегія: в production моніторингу використовуй reference-free (faithfulness + answer relevancy). Для CI/regression — додавай precision, recall, correctness на labeled test set.

Онлайн vs офлайн eval

  • Offline: зарані складений golden set, запускається в CI перед деплоєм.
  • Online: LLM-as-judge по кожному трейсу; human annotation queue; thumbs up/down; дrift detection.
  • Hybrid: 5% трафіку на human review, решта — automated scores.

Практична порада

«Починай з десятка ручних прикладів, які символізують реальні користувацькі сценарії. Потім автоматизуй через Ragas/Promptfoo. Без golden set ти літаєш всліпу».

3. Оптимізація: cost, latency, quality

Вибір моделі та роутинг

Задача Моделі (приклади) Примітки
Класифікація / extraction gpt-4o-mini, gemini-flash, claude-haiku Дешево, швидко, достатньо для структурованих задач
Reasoning / generation gpt-4o, claude-sonnet, grok-2 Краща якість, дорожче, повільніше
Довгі контексти / RAG claude-3.5-sonnet, gpt-4o-128k Велике вікно, добре інструкційне слідування
Coding / JSON claude-sonnet, gpt-4o Надійніший structured output

Способи зменшити вартість

  • Кешування: Helicone edge cache, Redis cache, semantic cache (embed query, шукати схожі).
  • Batch API: OpenAI Batch API знижує вартість на 50% для асинхронних задач.
  • Flex processing: OpenAI Flex — нижча ціна за рахунок латентності.
  • Коротші промпти: видаляй зайвий контекст, summary замість повного чанка.
  • Fine-tuning: зменшує потребу в few-shot, робить можливим дешевші моделі.
  • Model distillation / SLM: phi-4, qwen, mistral-small для простих задач.

Способи зменшити латентність

  • Streaming: stream: true, SSE/WebSocket, показуй користувачеві перш токен швидше.
  • Менше max_tokens / stop sequences, щоб уникнути зайвої генерації.
  • Batching: об'єднуй запити, де можливо (provider batching).
  • Менші моделі для швидких задач, дорогі — тільки коли треба.
  • Кеш та pre-computation: часті запити → відповідь з Redis.

Трикутник trade-off

Зазвичай можна обрати дві з трьох. На співбесіді говори так: «Ми визначаємо, яка метрика домінує для конкретного use case: для real-time chat — latency, для bulk processing — cost, для compliance review — quality. І підбираємо модель, caching та eval під це».

4. RAG & embeddings

Pipeline

  1. Ingestion: завантаження, парсинг (OCR для PDF/img), очищення.
  2. Chunking: document-aware (не різати таблиці/код), recursive fallback, overlap 10–20%.
  3. Embedding: OpenAI text-embedding-3 (large/small), Cohere Embed v3, BGE-M3 (self-hosted).
  4. Storage: pgvector, Qdrant, Pinecone, Weaviate, Chroma (тільки для прототипів).
  5. Retrieval: dense + sparse (BM25/Postgres FTS), reranker (Cohere Rerank, cross-encoder), Reciprocal Rank Fusion.
  6. Generation: top-k 3–5 чанків, зрозумілий prompt.

Ключові помилки в продакшені

  • Поганий chunking — найбільший внесок у погану якість. Не різати семантичні одиниці.
  • Місматч embedding-моделі — індекс і query мають бути однією версією моделі. Версіонуй.
  • Відсутність reranker — top-k з vector search слабкі; reranker покращує precision 15–25%.
  • Переповнення контексту — краще 3–5 якісних чанків, ніж 20 слабких.
  • Відсутність онлайн-моніторингу — не бачиш, коли документи застаріли або embedding зламався.

Hybrid search

Vector + keyword. Alpha 0.6–0.7 (на користь вектора) зазвичай оптимальний. Keyword ловить абревіатури, ID, власні терміни, які embeddings можуть пропустити.

5. Observability: Helicone, Langfuse, LangSmith, LangChain

Інструмент Архітектура Сильні сторони Коли обрати
Helicone Proxy — зміна baseURL, один header 5-хвилинна інтеграція, cost tracking, edge cache, gateway 100+ моделей, real-time alerts Швидкий старт, фокус на cost/latency
Langfuse SDK / OpenTelemetry Open-source (MIT), self-host free, глибокі eval, prompt management, datasets, human annotation Потрібна прозорість, eval, self-host, не-LangChain стек
LangSmith SDK / env vars Найкращий для LangChain/LangGraph, agent trajectory, CI/CD gating, вбудовані evaluators Якщо весь стек — LangChain/LangGraph
LangChain Фреймворк / бібліотека Абстракції для chains, agents, RAG, tool use; швидкий PoC Прототипи або коли команда вже на LangChain

Що моніторити

  • Cost per request, per user, per feature, per model.
  • Latency (TTFT, total), p50/p95/p99.
  • Token usage (input/output), cache hit rate.
  • Quality scores (faithfulness, relevancy, correctness) — online/offline.
  • Errors: rate limits, timeouts, validation failures, hallucination rate.
  • Prompt drift: суттєві зміни в розподілі виходів.

Helicone: практичні headers

  "Helicone-Property-Feature": "campaign-generator",
  "Helicone-Property-Environment": "production",

Custom Properties — ключ до сегментації: cost by feature, quality by user type, latency by environment.

6. Надійність та безпека LLM

Fallback та resilience

  • Primary → fallback model (напр. gpt-4o → claude-sonnet).
  • Circuit breaker при rate limit чи тривалих падіннях.
  • Exponential backoff + jitter, idempotency keys.
  • Timeout + користувацький повідомлення: «Запит обробляється, прийдемо по email».

Prompt injection та безпека

  • Input validation & sanitization, обмеження довжини.
  • Відокремлення інструкцій і контенту через теги/Delimiters.
  • Output validation: не допускай direct execution без review.
  • Helicone LLM Security / PromptArmor / власний guard.
  • Ніколи не зберігай секрети в system prompt.

Output validation

  • JSON schema validation, type checking, range checks.
  • Faithfulness guard: перевірка, що відповідь ґрунтується на retrieved context.
  • Refusal detection / moderation.

7. Self-hosting та fine-tuning

Self-hosting моделей

  • vLLM, TGI, Ollama — для inference на GPU.
  • Quantization (AWQ, GPTQ, GGUF) — зменшує VRAM, трохи знижує якість.
  • Batching (continuous batching в vLLM) для throughput.
  • Trade-off: ops overhead, GPU cost, latency vs API.

Fine-tuning

  • Доцільний, якщо: стабільний датасет, 100+ прикладів, потрібна конкретна тональність/формат, few-shot занадто дорогий.
  • LoRA / QLoRA — ефективні методи; full fine-tune — дорого.
  • Дані: quality > quantity, diversity, eval set незалежний від train.
  • Після fine-tuning — обов'язково run regression eval.

8. Real-time: WebSockets / SSE

Коли що

  • SSE (Server-Sent Events): односпрямований потік від сервера. Ідеальний для streaming LLM tokens у браузер. Простіший у масштабуванні (HTTP).
  • WebSockets: дуплекс, корисний для чат-інтерфейсів, collaborative editing, real-time notifications.

Реалізація

  • Бекенд: Koa/Express/Rails ActionCable/AnyCable; Ruby — faye-websocket або anycable.
  • Фронтенд: EventSource для SSE, WebSocket API або Socket.io.
  • Redis Pub/Sub або RabbitMQ для broadcast між серверними інстансами.
  • Обробка реконекції, heartbeat, backpressure, cleanup.
