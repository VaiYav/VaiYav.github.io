React + TypeScript

React Context

  • Коли використовувати: інфрідентно змінний глобальний стан: тема, мова, auth, feature flags, UI layout. Не для часто оновлюваних даних.
  • Чому: кожне оновлення Context ререндерить усіх споживачів. Для частих оновлень — Zustand/Redux Toolkit або колокальний стан.
  • Патерн: розділяти контексти за доменом (AuthContext, ThemeContext, FeatureFlagsContext), а не один гігантський.
  • Інтерв'ю: «Я використовую Context для статичних/рідкісних глобальних речей, а TanStack Query — для всього, що приходить з сервера».

TanStack Query (React Query)

  • Server state: автоматичне кешування, background refetch, stale-while-revalidate, deduplication, retries.
  • Mutation: optimistic updates, rollback on error, invalidation via queryClient.invalidateQueries.
  • Для AI: тривалі мутації, streaming responses, polling статусу довгих LLM-задач.
  • Питання на співбесіді: як обробляєш помилки, які staleTime/cacheTime вибираєш, як invalidates після mutation, як робиш optimistic UI?

Koa.js

Koa — мінімалістичний Node.js-фреймворк. Ймовірно, використовується для LLM-проксі/адаптера або окремого мікросервісу.

  • Контекст: все — req, res, state — лежить в ctx. Middleware — async функції (ctx, next) =>.
  • Cascading middleware: middleware йдуть по черзі, потім «розгортаються» назад. Порядок реєстрації критичний.
  • Екосистема: @koa/router, koa-bodyparser, @koa/cors, koa-helmet, koa-compress.
  • Для LLM: stream response від провайдера через ctx.body = readableStream, rate limiting, validation, transform payload.
// Приклад middleware-ланцюжка (Koa)
app.use(helmet());
app.use(cors({ origin: process.env.ALLOWED_ORIGINS }));
app.use(rateLimit({ windowMs: 60_000, max: 100 }));
app.use(bodyParser({ jsonLimit: '1mb' }));
app.use(authMiddleware);
app.use(routes.routes()).use(routes.allowedMethods());

Що сказати: «Koa хороша, коли треба максимальний контроль над request lifecycle, наприклад для stream-проксі між фронтендом і LLM API, з проміжним логуванням у Helicone».

Ruby on Rails

Контролери та API

  • RESTful ресурси, before_action, серіалізатори (ActiveModel::Serializer / jbuilder / fast_jsonapi), policy objects.
  • Версіонування API через namespace або Accept-Version header.
  • Обробка помилок:统一ний формат JSON, логування, instrumentation.

Моделі та БД

  • ActiveRecord, міграції, валідації, scopes, transactions.
  • PostgreSQL: JSONB для гнучких схем, масиви, full-text search, CTE, оконні функції.
  • N+1: eager load (includes, preload, joins), bullet gem, log analysis.

Background jobs

  • Sidekiq (Redis): дедлайнс, retries, queues, dead set, unique jobs.
  • RabbitMQ (в стеку): брокер повідомлень для decoupling між сервісами, event bus, durable queues.
  • Ідемпотентність: pass ID, not objects; idempotency key; lock row; unique lock з TTL.

Тестування (RSpec)

  • Unit, request, integration, feature tests. FactoryBot, Faker, VCR/WebMock для зовнішніх API.
  • Shared examples, custom matchers, test doubles, mocking Sidekiq/RabbitMQ.
  • Для LLM: mock HTTP-клієнта, golden-set assertions, freeze часу/UUID.

PostgreSQL

  • Оптимізація запитів: EXPLAIN ANALYZE, індекси (B-tree, GIN, GiST), partial/composite indexes, covering indexes.
  • JSONB: схема, що еволюціонує, але не без гранич: GIN-індекси, оператори @>, ?.
  • Full-text search: to_tsvector + to_tsquery, власні dict, ts_rank, збережені векторні колонки.
  • pgvector: не вказаний явно, але якщо робиш RAG — запитай, чи планують pgvector (ivfflat/hnsw). Або окремий векторний store.
  • Питання: як боротися з блокуваннями, deadlocks, long transactions, vacuum, partitioning для великих таблиць.

Redis & RabbitMQ

Redis

  • Кеш (Rails.cache / redis-store).
  • Сесії, rate limit (sliding window).
  • Pub/Sub для real-time notifications.
  • Sidekiq-черги.
  • Cache invalidation стратегії: key-based, TTL, cache tags.

RabbitMQ

  • Message broker, а не просто черга.
  • Exchanges (direct, topic, fanout), durable queues, ack/nack.
  • Decoupling сервісів: продюсер не знає про споживачів.
  • Порівняно з Sidekiq: RabbitMQ краще для міжсервісної комунікації, Sidekiq — для внутрішніх background jobs.
  • Dead letter exchanges, retry with TTL, idempotency.

LLM-інтеграція

Уніфікований адаптер для OpenAI / Grok / etc.

  • Абстракція над різними провайдерами: спільний інтерфейс, адаптери під кожен API.
  • Обробка streaming: Server-Sent Events (SSE) або raw chunked responses.
  • Таймаути, retries, exponential backoff, circuit breaker.
  • Rate limiting, token budgeting, model routing (strong vs cheap).

Helicone

  • Proxy-інтеграція: змінити baseURL на https://oai.helicone.ai/v1 + Helicone-Auth header.
  • Логування, вартість, латентність, токени, кастомні property.
  • Edge-кешування: Helicone-Cache-Enabled: true, Cache-Control.
  • LLM security: Helicone-LLM-Security-Enabled: true.
  • Alerts через Slack/email/webhook на threshold.

Контейнеризація та CI/CD

Kubernetes

  • Deployment, Service, Ingress, ConfigMap/Secrets, HPA, PDB, readiness/liveness probes.
  • Migrations: як Job/init container, щоб не ганяти з кожного пода одночасно.
  • Secrets: Kubernetes Secrets + external secret operator (Vault, AWS SM), ніколи не комітити.

GitLab CI

  • Етапи: build → test → lint/security scan → publish image → deploy.
  • Docker image з commit SHA tag, кешування, BuildKit.
  • Тести: RSpec, Jest, статичний аналіз (ESLint, RuboCop).
  • Security: Trivy, SAST, secret detection.
  • Deploy: або прямий kubectl, або краще — GitOps (ArgoCD/Flux): CI пушить зміну тегу в git, reconciler накатує.

Для Rails + React: multi-stage Dockerfile — build stage з Node, runtime — Ruby only. SECRET_KEY_BASE_DUMMY=1 для assets:precompile.

Jest (фронтенд-тести)

  • Unit: pure functions, hooks, utilities. Mock TanStack Query, MSW для API.
  • Component: React Testing Library, user-centric queries, avoid implementation details.
  • Integration: test flows, optimistic updates, error boundaries.
  • Coverage: aim for high-value paths, а не 100% ради цифри.
